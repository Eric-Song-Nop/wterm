# Ghostty Core

The `@wterm/ghostty` package provides a full-featured terminal emulation core powered by [libghostty](https://ghostty.org) built directly from upstream source. It implements the same `TerminalCore` interface as wterm's built-in Zig core, so it's a drop-in replacement.

## Why use it?

wterm ships with a lightweight built-in core (~12 KB WASM) that covers basic VT100/VT220/xterm escape sequences. For apps that need comprehensive terminal emulation — full Unicode grapheme clusters, all SGR attributes, terminal modes, and more — `@wterm/ghostty` provides all of that via Ghostty's battle-tested VT parser (~600 KB WASM).

Ghostty's native OSC 8 metadata is preserved through the active viewport, scrollback, and reflow. The DOM renderer resolves it into safe HTTP and HTTPS anchors without exposing Ghostty's page-local numeric IDs.

## Install

```bash
npm install @wterm/ghostty
```

## Usage

Load the Ghostty core and pass it to `WTerm` via the `core` option. Everything else stays the same.

### Vanilla JS

```ts
import { WTerm } from "@wterm/dom";
import { GhosttyCore } from "@wterm/ghostty";
import "@wterm/dom/css";

const core = await GhosttyCore.load();
const term = new WTerm(document.getElementById("terminal"), { core });
await term.init();
```

### React

```tsx
import { Terminal } from "@wterm/react";
import { GhosttyCore } from "@wterm/ghostty";
import "@wterm/dom/css";

const core = await GhosttyCore.load();

function App() {
  return <Terminal core={core} />;
}
```

### Vue

```vue
<script setup lang="ts">
import { Terminal } from "@wterm/vue";
import { GhosttyCore } from "@wterm/ghostty";

const core = await GhosttyCore.load();
</script>

<template>
  <Terminal :core="core" />
</template>
```

## Bundlers

The WASM binary is fetched at runtime rather than inlined, so the default has to resolve to a URL your app serves. `GhosttyCore.load()` resolves it with `new URL("../wasm/ghostty-vt.wasm", import.meta.url)`. Bundlers that implement that asset pattern emit the binary and rewrite the URL. Ones that do not leave `import.meta.url` pointing at the machine that built the bundle, and `load()` throws an error saying so.

When the default cannot work, serve the binary yourself and point at it:

```bash
cp node_modules/@wterm/ghostty/wasm/ghostty-vt.wasm public/ghostty-vt.wasm
```

```ts
const core = await GhosttyCore.load({ wasmPath: "/ghostty-vt.wasm" });
```

The binary is also addressable as `@wterm/ghostty/ghostty-vt.wasm`, so a bundler with a URL import can take it directly.

## Shared runtime and checkpoints

Node.js can load the committed binary once and host multiple independent cores in the same WASM instance:

```ts
import { readFile } from "node:fs/promises";
import { GhosttyCore, GhosttyRuntime } from "@wterm/ghostty";

const bytes = await readFile(new URL("./ghostty-vt.wasm", import.meta.url));
const runtime = await GhosttyRuntime.load(bytes);
const authority = GhosttyCore.fromRuntime(runtime, { effects: "authority" });
const replica = GhosttyCore.fromRuntime(runtime, { effects: "discard" });
```

`runtime.engineId` is generated from the exact Ghostty source tree and commit, snapshot schema, adapter source and ABI, build/feature profile, patchset, Zig version, and committed WASM SHA-256. Peers must require exact equality before exchanging snapshots. The generated `GHOSTTY_TERMINAL_PROFILE.term` is also the `TERM` value the Host supplies to its child process.

URL and byte loads verify the raw WASM digest and set `runtime.artifactVerified` to `true`. The WebAssembly API cannot recover bytes from a precompiled `WebAssembly.Module`, so that input verifies only its embedded source build ID, sets `artifactVerified` to `false`, and is an explicit trust assertion by the caller.

The authority can encode semantic key, paste, and focus input with `encodeKey()`, `encodePaste()`, and `encodeFocus()`. Browser code normalizes keyboard input once with `ghosttyKeyEventFromDom(event)` and sends that object unchanged; the Host passes it directly to `encodeKey()` against authoritative modes rather than implementing another DOM normalization path. The helper preserves physical code, logical key, UTF-8 text, action, AltGraph, composition, and consumed modifiers, while removing AltGraph's browser-synthesized Ctrl+Alt pair. After applying PTY output, `drainEffects()` returns Ghostty's binary PTY replies in production order. Its queue is bounded to 256 frames and 64 KiB. Overflow throws a fatal `GhosttyMutationError` and poisons the core; the Host must terminate the session and must not retry the already-applied write.

`encodeSnapshot()` returns a point-in-time Ghostty binary checkpoint, including any unfinished parser continuation available through `getContinuation()`. A snapshot is not an ordered event protocol; the ordered PTY byte stream remains authoritative between checkpoints.

## How it works

`@wterm/ghostty` builds libghostty directly from the auditable [Eric-Song-Nop/ghostty fork](https://github.com/Eric-Song-Nop/ghostty) — no build-time source rewriting, third-party npm packages, or pre-built binaries from other projects. The architecture:

1. **Exact Zig package dependency**: Fork commit `fe317f850c3ab212f6638122c459b9b48b99a016`, based on upstream `f2d5758f6305867dc36b36293c6165d8152b853e`, is declared in `zig/build.zig.zon`. Its [single reviewed patch](https://github.com/Eric-Song-Nop/ghostty/pull/1) fixes ANSI DECRQM dispatch; Zig's package manager fetches the immutable commit automatically.
2. **Upstream WASM support**: The pinned revision builds for `wasm32-freestanding` without rewriting Ghostty source files.
3. **WASM export layer**: `zig/src/wasm_api.zig` imports Ghostty's `Terminal`, `TerminalStream`, snapshot, input, and `RenderState` APIs and exposes the stable adapter ABI to JavaScript.
4. **Generated engine provenance**: `generate-engine.mjs` embeds a source build ID, then generates an exact engine ID from canonical provenance including the committed WASM SHA-256. Tests reject stale generated files or binary content.
5. **Committed WASM binary**: The built `wasm/ghostty-vt.wasm` is checked into the repo so consumers never need Zig installed.
6. **TypeScript runtime**: `wasm-bindings.ts` loads URLs, bytes, or precompiled modules, verifies artifact bytes where the Web API exposes them, always verifies the embedded build identity, and provides typed accessors.
7. **TerminalCore adapter**: `ghostty-core.ts` implements the `TerminalCore` interface and the authority/checkpoint primitives.

The `TerminalCore` interface means the DOM renderer, input handler, and framework bindings don't need to know which core they're talking to.

Ghostty enables grapheme clustering and returns combining sequences and ZWJ emoji through `CellData.chars`. The same complete strings are available from active cells and scrollback.

The pinned revision does not expose a cumulative discarded-row count. The optional `TerminalCore.getScrollbackDiscardedCount()` signal is omitted rather than approximated from retained history.

Terminal applications can query the Ghostty core's foreground and background colors with OSC 10 and OSC 11. The core starts with its configured colors and tracks later OSC color changes and resets.

Ghostty also exposes synchronized-output mode (`CSI ? 2026 h/l`) and its generation to the DOM renderer, so updates inside a synchronized block paint as one final frame.

## Rebuilding the WASM

Only needed by maintainers. Requires exactly [Zig 0.16.0](https://ziglang.org/download/):

```bash
pnpm --filter @wterm/ghostty rebuild-wasm
```

When the host toolchain cannot build, run the same script in a Linux container:

```bash
pnpm --filter @wterm/ghostty rebuild-wasm:docker
```
